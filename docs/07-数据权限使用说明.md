# 数据权限使用说明

> 后端文档｜角色 `data_scope` 如何配置、在用户/部门等查询中如何生效、新业务怎么接入

---

## 一、怎么用（运营 / 测试）

### 1. 配置角色数据范围

路径：**系统管理 → 角色管理 → 数据权限**

| 值 | 含义 | 用户列表效果 | 部门列表/树效果 |
|----|------|--------------|-----------------|
| **1** 全部 | 不按部门过滤 | 可见全部用户 | 全树 |
| **2** 自定 | 勾选 `sys_role_dept` | 仅勾选部门下用户 | 仅勾选部门（树保留祖先） |
| **3** 本部门 | 当前用户 `dept_id` | 同部门用户 | 仅本部门 |
| **4** 本部门及以下 | 本部门 + ancestors 子孙 | 本部门及下级用户 | 本部门及下级 |
| **5** 仅本人 | 当前 `user_id` | **只有自己** | **只有自己所在部门** |

保存后会 `evict` 该角色 RBAC 缓存。被测账号点导航栏 **刷新权限**（或重新登录），再打开用户/部门页验证。

### 2. 账号前提（否则看起来「没效果」）

1. **超级管理员 `userId=1` 永远看全库**（唯一行级豁免），改其角色的 `data_scope` 也不会过滤。请用 **非 1 号**账号验证。  
2. 「管理员」角色（`role_key=admin`）**会按 `data_scope` 过滤**——设成「本部门」后，该角色下非 1 号用户只能看本部门。  
3. 「本部门 / 本部门及以下」要求当前用户已绑定 **`dept_id`**；未绑部门时过滤结果为空。  
4. 改完角色范围后点 **刷新权限**（或重新登录）；保存数据权限时后端已 `evict` 角色缓存，列表会读新 `data_scope`。  
5. 若同一账号绑了多个角色，**任一角色为「全部」则仍看全库**（角色范围取并集）。

### 3. 与菜单权限的关系

- **菜单/按钮**：`sys_role_menu` → `permsSet` / 动态路由（能不能进页面、点按钮）。  
- **数据范围**：`sys_role.data_scope` + 可选 `sys_role_dept`（进了页面后能看到哪些行）。  
两者独立；有「用户查询」菜单但仍可能只看到本人一行。

## 二、已接入范围（本仓）

| 模块 | 列表 SQL `@DataScope` | 单条/写操作 | 树 |
|------|----------------------|-------------|-----|
| **用户管理** | `SysUserController` `/list` `/listAll` `/export` | `assertCanAccessUser` / `assertCanAssignDept` | 左侧部门树走 `/sys/dept/getSysDeptTree`（按可见部门裁剪） |
| **部门管理** | `SysDeptController` `/list` `/listAll`（`deptAlias=sd`） | `assertCanAccessDept` | `getSysDeptTree`、`roleDeptTreeselect` 用 `DataPermissionHelper.filterDeptTree` |
| **角色数据权限** | — | 设「全部」需 `canAssignAllDataScope`（userId=1 / userType=1 / 超管 role_key）；自定部门须在操作者可见范围内 | `roleDeptTreeselect` |

关键类：

- 切面：`DataScopeAspect`  
- 单条/树辅助：`DataPermissionHelper`  
- 豁免：`AdminAuthUtils.isDataScopeBypass`（**仅 userId=1**）  
- 授予「全部」：`AdminAuthUtils.canAssignAllDataScope` 
- 角色范围缓存：`RbacCacheService.getRoleDataScope` / `getRoleDeptIds`

## 三、新业务怎么接（开发）

主路径与**系统一致**（注解挂 **Controller**，不要只挂 `@Transactional` Service）：

```text
@Controller @DataScope list(SysUser/SysDept)
  → DataScopeAspect：clear → 按角色拼 SQL → params.dataScope = " AND /*GP_DATA_SCOPE*/ (...)"
  →（用户列表）prepareDeptFilter：展开部门树 IN，须在 startPage 之前，避免 PageHelper 被子孙部门查询抢先消费
  → startPage()（PageHelper，可选）
  → Service → Mapper XML：${params.dataScope}
  →（兜底）DataScopeInterceptor 改 BoundSql（须拦 4+6 参 query）
```

### 列表查询

1. 查询实体继承 `BaseEntity` 的 `params`（`getParams()` 懒创建）；**不要**在子类再声明一份 `params` 字段，否则切面写入与 MyBatis 读取可能不是同一 Map。  
2. **Controller 列表方法**上加 `@DataScope`（第一个入参为查询实体）：

```java
@DataScope
@GetMapping("/list")
public PageDataInfo list(SysUser q) {
  sysUserService.prepareDeptFilter(q);
  startPage();
  return getDataTable(sysUserService.selectSysUserList(q));
}

@DataScope(deptAlias = "sd")
@GetMapping("/list")
public PageDataInfo list(SysDept q) { ... }
```

3. Mapper XML **where 末尾**直接拼（勿再用 `<if>` 包一层导致 OGNL 判空失败）：

```xml
<!-- 数据范围过滤 -->
${params.dataScope}
```

切面会先 `params.dataScope=""` 防注入，再写入真实片段；空串对 SQL 无害。

4. 依赖：`spring-boot-starter-aop`（推荐显式）；`aspectjweaver` 多为传递依赖。  
   为何以前只有 weaver 时日志/防重也能用、与 DataScope 的关系：见 [10-SpringAOP切面为何生效与starter-aop.md](./10-SpringAOP切面为何生效与starter-aop.md)。

### 单条详情 / 改删

列表过滤防不住改 URL 调详情。对目标 `userId`/`deptId` 调用：

- `dataPermissionHelper.canAccessUser(loginUser, userId, deptId)`  
- `dataPermissionHelper.canAccessDept(loginUser, deptId)`  

无权限则返回错误，勿继续写库。

### 部门树（要保留祖先路径）——**有必要按数据范围过滤**

用户管理左侧筛选、新增/改用户选部门、角色「自定数据权限」勾选树等，一般系统（多数 RBAC 后台）都会按当前操作者的 `data_scope` **裁剪树**，原因：

| 若不过滤 | 风险 |
|----------|------|
| 左侧点「看不见」的部门 | 列表 SQL 有 `@DataScope` 会查出空，体验像坏了；或误以为有权限 |
| 表单可选超范围部门 | 写库时虽可再拦，但 UI 已越权展示 |
| 给角色勾选不可见部门 | 权限放大 |

**不要**对树接口只挂 `@DataScope` 砍 SQL：子部门可见而父节点被删时树会断。正确模式：

```java
Set<Long> visible = dataPermissionHelper.resolveVisibleDeptIds(loginUser);
return dataPermissionHelper.filterDeptTree(fullTree, visible); // 可见节点 + 祖先路径
```

`visible == null` 表示不限制（仅 `userId=1` 或角色含「全部」）。

本仓已接入：

| 接口 | 用途 | 是否按范围裁剪 |
|------|------|----------------|
| `GET /sys/dept/getSysDeptTree` | 用户筛选 / 选部门 / 个人资料 | ✅ `filterDeptTreeForCurrentUser` |
| `GET /sys/dept/roleDeptTreeselect/{roleId}` | 角色自定数据权限勾选 | ✅ 同上 + `checkedKeys` |
| `GET /sys/dept/list` | 部门管理表格 | ✅ Controller `@DataScope` |

写操作仍须 `canAccessDept` / `canAccessUser`，防改 URL 绕过树 UI。

### 别名约定（避免拼错列）

| 场景 | 注解 | 生成片段示例 |
|------|------|----------------|
| 用户无别名 | `@DataScope` | `user_id` / `dept_id` / `create_by` |
| 用户有别名 `su` | `@DataScope(deptAlias="su", userAlias="su")` | `su.user_id`、`su.dept_id` |
| 部门别名 `sd` | `@DataScope(deptAlias="sd")` | `sd.dept_id`；仅本人 → `sd.dept_id = 我的部门` |

## 四、自检清单

- [ ] 用 **非 userId=1**、已绑 `dept_id` 的账号测本部门/仅本人  
- [ ] SQL 中出现 `/*GP_DATA_SCOPE*/` 与 `dept_id` / `user_id` 条件  
- [ ] 改角色数据范围 → 刷新权限 → 用户列表 / 部门列表 / 部门树一致  
- [ ] 越权访问他人 `detail?userId=` / `detail?deptId=` 被拒  
- [ ] 新增用户所选部门不在可见范围时被拒  
- [ ] 角色「数据权限」页：`/sys/dept/roleDeptTreeselect/{roleId}` 可正常返回 `depts` + `checkedKeys`
